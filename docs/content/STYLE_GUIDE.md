# Стиль и правила текстов RailTech

## 1. Голос

* **Аудитория:** инженеры, снабженцы и тендерные отделы предприятий и госзаказчиков Узбекистана
  (железные дороги, промышленность). B2B/B2G.
* **Тон:** инженерный, точный, спокойный. Факты, параметры, стандарты, сроки — вместо эпитетов.
* **Нет:** «лучший», «уникальный», «инновационный», «№1», «мирового уровня», восклицательных знаков,
  эмодзи, канцелярита («осуществляет деятельность по…» → «поставляет»).
* **Да:** «В наличии на складе в Ташкенте», «Паспорт завода и сертификат соответствия»,
  «Счёт с НДС 12%», конкретные модели, ГОСТ, коды ТН ВЭД, единицы измерения.
* Первым идёт то, что важно покупателю: что это → для чего → ключевые параметры → условия поставки.

## 2. Факты — только подтверждённые

Сайт юридического лица; неверный факт — это претензия заказчика или тендерный риск.

* **Можно использовать без брифа:** данные из `src/data/cms/global.json` (реквизиты, адрес, телефон,
  метрики компании), уже опубликованные на сайте факты, общеизвестные технические сведения о типе
  изделия (назначение колёсной пары, что такое DDP) и данные из нормативных документов (ГОСТ),
  если вы уверены в них.
* **Только из брифа или источника, указанного в PR:** цены, наличие и количество, сроки поставки,
  характеристики конкретной модели, сертификаты, названия клиентов и заводов-партнёров, номера
  договоров, цифры проектов, отзывы, фото.
* Нет данных → не пишите поле (оно необязательное) или задайте вопрос; в PR раздел «Открытые
  вопросы». Слова `TODO`, `TBD`, `???` в тексте — ошибка проверки, их нельзя оставлять.
* Цена: поле `price` заполняется только числом из брифа (`125 000 000` — в сумах, с НДС). Иначе пусто —
  сайт покажет «Цена по запросу».
* Статус наличия: `status` — `В наличии` / `Резерв` / `Под заказ`; `statusKey` строго соответствует
  (`in_stock` / `reserved` / `on_order`).

## 3. Форматы

| Что | Правило | Пример |
|---|---|---|
| Кавычки | RU, UZ: «ёлочки»; EN: "прямые" | «RailTech» MChJ / RailTech LLC |
| Числа | RU/UZ: пробел тысяч, запятая дроби в прозе; EN: запятая тысяч, точка дроби | 1 200 / 1,200; 4,85 т в тексте, `4.85 t` в характеристиках допустимо |
| Единицы | через пробел, по ГОСТ 8.417 | 1850 мм, 23,5 тс/ось, 3,3 кВ |
| Деньги | сумма + UZS/сум, «с НДС 12%» | 125 000 000 сум с НДС 12% |
| Даты | `publishDate` в формате `YYYY-MM-DD`; в тексте — словами | 2026-03-12; 12 марта 2026 г. |
| Модели, артикулы, ГОСТ | не переводятся и не транслитерируются (кроме кириллицы в моделях: `СА-3` → `SA-3`) | GOST 9246-2013, RT-RS-118 |
| SKU | `RT-<ГРУППА>-<NNN>`, группы: RS — подвижной состав, SCB — СЦБ, TRK — путь, ELC — энергетика, KIP — КИП | RT-RS-120 |
| CAD-коды разделов | ЗАГЛАВНЫЕ, через `//`, одинаковые во всех языках | `SRV.05`, `LAB 06` |
| Заголовки в Markdown | начинать с `###` (H1 и H2 занимает страница) | `### Назначение` |

## 4. Переводы

* **Смысловой перевод, не подстрочник.** Сохраняйте факты, числа, модели, единицы; меняйте порядок
  слов и обороты под язык. Длина UZ/EN — примерно как у RU (± 30%), не короче половины.
* **Узбекский:** латиница, апостроф `'` (`o'`, `g'`, `ma'lumot`, `ta'minot`), без кириллицы. Термины —
  только по [GLOSSARY.md](./GLOSSARY.md). Деловой нейтральный стиль, обращение на «siz».
  Аббревиатуры по-узбекски: QQS (НДС), STIR (ИНН), TIF (ВЭД), SMB (СЦБ), EHF (ЭСФ).
* **Английский:** деловой международный, US spelling; термины по GLOSSARY. Не «Uzbekistan Republic»,
  а «the Republic of Uzbekistan»; «LLC», не «OOO».
* Если перевод термина не очевиден: найдите его в существующем контенте сайта; нет — добавьте строку
  в GLOSSARY.md в том же PR и отметьте это в описании PR для проверки носителем языка.
* Списки (`metrics`, `tags`) — одинаковое количество элементов во всех языках, в том же порядке.

## 5. Структура текстов по типам

* **Товар (body ≥ 150 знаков, лучше 400–800):** назначение и где применяется → конструкция/состав →
  ключевые параметры (подробные — в `attributes`) → комплектность и документы → условия поставки.
* **Услуга (≥ 300):** какую задачу решает → что входит (список) → результат для заказчика → документы.
  Этапы — в `steps` (3–5), параметры — в `benefits`.
* **Проект (≥ 300):** задача заказчика → решение RailTech → результат в цифрах (только подтверждённые)
  → что можем повторить. Имена клиентов — только с разрешения (в брифе).
* **Статья (≥ 1200, лучше 3000–6000):** практическая польза для инженера/снабженца: как рассчитать,
  выбрать, оформить; пример/таблица; вывод и ссылки на товары/услуги сайта (SEO.md §5).
