# Архитектура сайта railtech.uz (v2, ноябрь 2026)
Статус: действует · Обновлено: 2026-11-23 · Прежняя версия (HUD/CAD-портал с каталогом) — ветки `archive/legacy-v1-main`, `archive/legacy-v1-content`

Этот документ — единственная правда о том, **какие страницы есть, откуда берутся данные и как сайт связан с платформой**.
Агент или разработчик, который хочет добавить страницу, раздел, поле CMS или компонент, сначала правит этот документ
(в том же PR). Всё, чего здесь нет, на сайте не появляется.

## 1. Назначение

Сайт — визитка компании ООО «RailTech»: **о компании, о её возможностях и приглашение к работе через Кабинет**.
Сделки, каталог позиций, цены, документы и переписка живут не на сайте, а на платформе RailTech
(репозиторий `nzulkaynarov/RailTech_Platform`): CRM принимает заявки, Кабинет (`cabinet.railtech.uz`) — работа с
клиентами и партнёрами.

Позиционирование: RailTech поставляет оборудование и услуги **предприятиям и организациям** Узбекистана и представляет
интересы международных производителей в регионе. Сайт **не** привязан к одной отрасли: в общих текстах, шапке,
SEO и навигации нет «ж/д», серий локомотивов и отраслевых каталогов (проверяет `scripts/check-content.mjs`, правило
`positioning`). Отрасль партнёра или события упоминается только в фактах о нём (статья о партнёре, новость).

## 2. Карта страниц

Все страницы существуют на трёх языках: `/…` (ru, по умолчанию), `/uz/…`, `/en/…`. Файлы — в `src/pages/[...lang]/`.

| Маршрут | Файл | Что это | Источник данных |
|---|---|---|---|
| `/` | `index.astro` | Главная: первый экран, мост (барьеры), возможности, о компании, производители, Кабинет, новости, заявка | `data/cms/home.json`, `company.json`, коллекция `partners`, коллекции `services`, `news` |
| `/services/` | `services/index.astro` | Обзор услуг: «Заказчикам» и «Партнёрам» | `pages.json → services`, коллекция `services` |
| `/services/<slug>/` | `services/[slug].astro` | Услуга: `supply`, `engineering` (заказчикам), `representation`, `localization` (партнёрам) | коллекция `services` |
| `/news/` | `news/index.astro` | Лента: новости, статьи, проекты, партнёры (фильтр по типу) | коллекция `news`, `pages.json → news` |
| `/news/<slug>/` | `news/[slug].astro` | Материал или статья о партнёре (`partner-<id>`); внизу — рекомендации, у партнёра — «Материалы о партнёре» | коллекции `news`, `partners` (`src/utils/feed.ts`) |
| `/contacts/` | `contacts.astro` | Контакты, реквизиты, форма заявки | `company.json`, `pages.json → contacts` |
| `/privacy/`, `/terms/`, `/cookies/` | `privacy.astro`, `terms.astro`, `cookies.astro` | Сервисные страницы (только в футере) | `data/cms/legal.json` |
| `/404` | `src/pages/404.astro` | Страница не найдена | `pages.json → notFound` |
| `/admin/` | `src/pages/admin.astro` | Sveltia CMS (версия зафиксирована) | `public/admin/config.yml` |
| старые адреса v1 (`catalog`, `blog`, `projects`, `about`, …) | `src/pages/[...legacy].astro` | Перенаправления для ru/uz/en (meta refresh + canonical, `noindex`, вне sitemap) | `src/data/legacy-redirects.json` |

Навигация (шапка): **Услуги · Новости · Контакты** + переключатель языка + кнопки **«Начать работу»** (форма заявки,
`/contacts/#request`) и **«Войти в Кабинет»** (`company.json → cabinet.url` + `/login`). Футер: разделы, сервисные страницы,
контакты, ИНН. Меню одно — футер и мобильное меню строятся из `src/utils/nav.ts`.
На телефоне (≤ 760 px) внизу экрана закреплена **панель связи** (`MobileBar`): «Начать работу» (та же форма заявки),
Telegram и звонок — это не вторая навигация, а те же действия шапки, которые на телефоне спрятаны в «Меню».
Панель скрывается, пока посетитель печатает в поле формы.

## 3. Модель данных

Тексты не пишутся в коде (`.astro`, `.tsx`, `.ts`). Всё редактируется в `/admin`.

| Где | Что | Переводы |
|---|---|---|
| `src/data/cms/company.json` | Реквизиты, адреса, контакты, Telegram, ссылки Кабинета, адрес приёма заявок, цифры («5+ лет» и т. д. — правит владелец) | блоки `uz`/`en` |
| `src/data/cms/home.json` | Тексты блоков главной (первый экран, мост, возможности, о компании, Кабинет, заявка) | блоки `uz`/`en` |
| `src/data/cms/pages.json` | Заголовки и вводные тексты страниц «Услуги», «Новости», «Контакты», 404 | блоки `uz`/`en` |
| `src/data/cms/legal.json` | Политика конфиденциальности, условия использования, cookies | блоки `uz`/`en` |
| `src/data/cms/seo.json` | title/description страниц, значения по умолчанию | блоки `uz`/`en` |
| `src/data/cms/ui/*.json` | Подписи интерфейса (кнопки, метки, формы) | `ru`/`uz`/`en` в одной записи |
| `src/content/services/*.md` | 4 услуги: аудитория, лид, коротко, шаги, что получает клиент/партнёр, требования, FAQ, тело | блоки `uz`/`en` (тело — `body` в блоке) |
| `src/content/news/*.md` | Материалы: `type` = `news` / `article` / `project`, дата, обложка, галерея (`gallery: [{image, alt}]`), `partners` и `services` (связи для рекомендаций), источники; в тексте — фото с подписью, цитаты, таблицы, сноски (`src/utils/markdown.ts`) | блоки `uz`/`en` (тело — `body` в блоке) |
| `src/content/partners/*.md` | Производитель-партнёр, **одна запись = плитка + статья**: `name` (бренд), `legalName` (юрлицо, к нему относится статус), `group`, `brands`, `country` (код), `status` (`dealer` / `direct`), `order`; статья — дата, заголовок, кратко, обложка, текст. Имя файла = id; статья выходит в «Новостях» как `/news/partner-<id>/` и делает плитку ссылкой, когда написаны заголовок и текст | блоки `uz`/`en` (бренд, юрлицо — сразу; статья — по этапу новостей) |
| `src/data/cms/ui/countries.json` | Названия стран для `country.<код>` (выбор страны партнёра в админке) | `ru`/`uz`/`en` в одной записи |

**Лента и рекомендации** (`src/utils/feed.ts`). «Новости» — это коллекция `news` и статьи партнёров одной лентой.
Связи между материалами не прописываются руками: страница партнёра показывает материалы с его `partners`; страница
услуги — материалы, у которых услуга выбрана в `services` или на неё есть ссылка в тексте (`/services/<slug>/`);
под материалом — материалы с теми же партнёрами, затем с теми же услугами, затем самые новые (`RelatedMaterials`).

**Формат переводов** (Sveltia CMS i18n, структура `single_file_default_root`): русские значения в корне файла,
переводы — те же поля в блоках `uz` / `en`, `lang` перечисляет включённые языки (ведёт админка). Пример и правила —
`docs/content/README.md` §2. Сайт читает данные через `localize(data, lang)` из `src/i18n/blocks.mjs` (блок языка
накладывается на русские значения, пустое → русское) и `tField()`; проверки контента видят те же данные через
`toSuffixed()`. Подписи интерфейса (`ui/*.json`) остаются в формате `{key, ru, uz, en}`.
В админке языки открываются рядом, кнопка «Перевести» (Claude, Gemini, Google и др.; ключ API хранится в браузере
редактора) заполняет пустые поля. Переводимые поля обязательны только на русском: полноту UZ/EN проверяет
`check-content` (вне «Новостей» — ошибка, в «Новостях» — счётчик).

Схема коллекций — `src/content/config.ts`; схема CMS — `public/admin/config.yml`. Они должны совпадать (проверяет
`scripts/validate-cms-config.mjs` при сборке).

**Один факт — одно место.** Телефон, e-mail, ИНН, домены, год основания и адреса хранятся только в `company.json`;
в остальных текстах вместо них стоят подстановки `{phone}`, `{email}`, `{inn}`, `{site}`, `{cabinet}`, `{foundedYear}`,
`{officeAddress}`, `{legalAddress}` (`src/i18n/facts.mjs`, заполняют `localize()` и `tField()` на языке страницы;
новости — исторические записи, в них факты пишутся текстом). `check-content` запрещает набирать эти значения текстом
и требует тех же подстановок в переводах, `check-build` — незаполненных подстановок на страницах.
**Вычисляемое не вводится:** « | RailTech» в title добавляет сайт (если бренда нет в заголовке и влезает 60 знаков),
юридические страницы — одна дата редакции на документ (`legal.json → <page>.edition`) и нумерация разделов по порядку,
ссылки Кабинета — от `cabinet.url`.

**Правила ввода в админке** (`config.yml`): формат реквизитов и ссылок (`pattern`, `type: url/email`), длина
«Кратко» и SEO (`minlength`/`maxlength` со счётчиком), подсказки (`hint`), адрес нового материала латиницей из
заголовка (глобальный `slug`: транслитерация, ≤ 80 знаков, правится при создании), дата по умолчанию — сегодня.
Услуги нельзя создавать и удалять; в подписях интерфейса правятся только тексты, ключи и состав закрыты.
`validate-cms-config` проверяет существующие данные по тем же правилам: иначе редактор не смог бы сохранить запись.

**Порядок перевода.** Этап задаёт `src/data/content-stage.json` (правит только владелец; логика в `src/utils/stage.ts`,
фильтре sitemap в `astro.config.mjs`, `scripts/check-content.mjs` и `scripts/check-build.mjs`).
- `ruOnly: true` — весь сайт RU-first: UZ/EN не заполняются, страницы `/uz/…` и `/en/…` показывают русский, `noindex`,
  их нет в sitemap. Сейчас `ruOnly: false`: русская версия одобрена, сайт трёхъязычный.
- `ruOnlySections` — разделы, которые на `/uz/` и `/en/` остаются русскими целиком (сейчас `[]`; новости переведены
  2026-11-23). Их контент выводится на RU (интерфейс вокруг переведён), эти страницы UZ/EN `noindex` и не
  попадают в sitemap, русская страница объявляет только hreflang `ru` и `x-default`; пропуски UZ/EN в разделе
  `check-content` считает, но не падает. Когда раздел переведён, владелец убирает его из списка.
- Вне этих разделов новый или изменённый текст пишется сразу на трёх языках; пропущенный UZ/EN — ошибка `check-content`.
  Флаг `check-content --ru-only` включает режим RU-first вручную (пропуски только считаются).
- **Материалы «Новостей» — по отдельности** (`src/utils/stage.ts → entryLangs`, `src/i18n/blocks.mjs → translatedLocales`):
  материал существует на языке, если язык включён в его `lang` и в блоке есть заголовок и (при русском тексте) текст.
  Иначе его страница на этом языке показывает русский, `noindex`, вне sitemap (`src/i18n/entry-langs.mjs` для
  `astro.config.mjs` и `check-build`), русская страница объявляет только существующие языки. Так редактор может
  опубликовать новость по-русски сразу и перевести позже; пропуски `check-content` только считает.

## 4. Компоненты

```
src/layouts/BaseLayout.astro        <head>: SEO, canonical, hreflang, JSON-LD, шрифты; Header + <main> + Footer
src/components/layout/              Header (меню, языки, кнопки), MobileMenu (<details>, без JS), Footer,
                                    MobileBar (панель связи внизу экрана на телефоне, без JS)
src/components/ui/                  Button, Section, SectionHead, Breadcrumbs, Faq (<details>), PartnerTiles, NewsCard,
                                    RelatedMaterials (рекомендации из src/utils/feed.ts), ArticleAside (боковая колонка
                                    одиночной страницы: карточка партнёра, связи, кнопка заявки), Toc («На странице»), Prose
src/components/home/                Hero, Bridge, Directions, About, CabinetBlock, LatestNews, Invite
src/components/islands/LeadForm.tsx единственный React-остров: форма заявки → CRM
src/styles/tokens.css, global.css   дизайн-токены и базовые стили (docs/DESIGN.md)
src/components/ui/Lightbox.astro    просмотр фото статьи на весь экран (<dialog>, стрелки, Esc, свайп)
src/scripts/motion.ts               плавная прокрутка колесом (Lenis), тень шапки, счётчики цифр (`data-count`);
                                    подключается в BaseLayout (DESIGN.md → «Движение»); появление блоков — чистый CSS
src/utils/fonts.ts                  файлы шрифтов для предзагрузки (font-display: optional — astro.config.mjs)
```

Правила: один компонент — одна задача; стили компонента — в его `<style>` через токены `var(--…)`, без литеральных цветов;
никакой декоративной «телеметрии» и псевдотерминальных подписей; иконки — inline SVG с `aria-hidden`.
Движение только прогрессивное: без JavaScript и при «уменьшить движение» в системе весь контент виден сразу и без анимаций.

## 5. Заявки и Кабинет (интеграция с платформой)

```
Посетитель ─ «Начать работу» ─► форма (LeadForm.tsx) ─► CRM: POST {leadEndpoint}        ─► лид «с сайта» в очереди
                                                          (токен: GET {leadEndpoint}/token)   менеджер связывается
                                                                                               и приглашает в Кабинет
Клиент/партнёр ─ «Войти в Кабинет» ─► cabinet.railtech.uz/login  (вход по коду из письма или Telegram, без пароля)
Telegram ─► t.me/<бот>?start=web  (бот CRM, источник «сайт»)
```

- Адреса берутся из `company.json`: `leadEndpoint` (по умолчанию `https://crm.railtech.uz/api/v1/leads/web`),
  `cabinet.url` (вход `/login` и приглашение `/new-client` строятся от него в `src/utils/company.ts`), `telegramBot`.
- Контракт приёма (платформа, `packages/contracts/openapi/crm.yaml`): `GET …/token` → `{token, expires_at, min_fill_seconds}`;
  `POST …` JSON `{name, company?, phone?, email?, text, language, form_token, consent: true, website: ""}` → `202 {lead_id}`;
  ошибки `422 validation_failed` (`details.reason`), `429 rate_limited`. Поле `website` — ловушка для ботов, всегда пустое.
- CRM принимает запросы только с разрешённых адресов (CORS). Чтобы форма работала с railtech.uz, на платформе в
  `infra/compose/prod.yml` к `CABINET_ORIGIN` добавляется адрес сайта. Пока этого нет, форма при ошибке сети показывает
  запасные каналы: Telegram, телефон, e-mail и ссылку `cabinet.url` + `/new-client`.
- Регистрации в Кабинете «с улицы» нет — только по приглашению менеджера. Поэтому на сайте нет кнопки «Зарегистрироваться».
- Сайт не ставит cookie и не подключает аналитику; данные заявки уходят только в CRM RailTech.

## 6. Сборка и проверки

| Команда | Что делает |
|---|---|
| `make install` | `npm ci` |
| `make dev` | локальный сервер `http://localhost:4321/rt-corporate-website/` |
| `make test` | unit-тесты (Vitest): i18n, SEO, форма заявки, навигация |
| `make check` | схема CMS, правила контента (этап перевода из `content-stage.json`), unit-тесты, `astro check`, сборка, аудит `dist/` |
| `make e2e` | Playwright по собранному сайту: страницы открываются, нет ошибок консоли, кнопки ведут куда нужно, нет горизонтальной прокрутки на телефоне, форма показывает ошибки и успех |
| `make ci` | всё вместе, как в GitHub Actions |

GitHub Pages, домен `railtech.uz`: публикация (`deploy.yml`) собирается с `CUSTOM_DOMAIN` (база `/`); локально и в
проверках PR база `/rt-corporate-website`. `main` = прод,
пуш в `main` запрещён, только PR.

## 7. Что не делаем

Не возвращаем каталог позиций и цены на сайт (они в Кабинете). Не вводим вторую навигацию, модальные окна заявки,
слайдеры с автопрокруткой, HUD-декор. Не добавляем аналитику и cookie без обновления `/cookies/` и решения владельца.
Не пишем тексты в коде. Не указываем дилерский статус без документа производителя и не публикуем основание статуса
(показывается клиенту по запросу).
